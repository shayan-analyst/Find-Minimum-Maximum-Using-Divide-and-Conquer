Find the smallest and the largest. Count every comparison.

The question this project answers, and the baseline we have to beat.

The task

Input
An array A of n integers
Output
min(A), max(A) and the number of element comparisons used
Method
Divide and conquer

The straightforward scan

min ← max ← A[1]
for i ← 2 to n
    if A[i] < min then min ← A[i]     // 1 comparison
    if A[i] > max then max ← A[i]     // 1 comparison

Two comparisons for each of the other n − 1 elements, so it always costs 2(n − 1).

Can divide and conquer use fewer?

Yes. For n = 2k it needs 3n/2 − 2, about 25% fewer. The next slides show where every one of those comparisons comes from.

Divide, conquer, combine

Three moves, repeated until the pieces are small enough to answer on sight.

Divide

Split A[low..high] at mid = ⌊(low + high) / 2⌋ into a left and a right half.

0 comparisons

Conquer

Solve both halves recursively. Stop at 1 element (min = max = that element) or 2 elements (one comparison).

0 or 1 comparison per leaf

Combine

Compare the two minimums, then the two maximums. Each combine step costs exactly two comparisons.

2 comparisons per merge

The algorithm

Read each line together with its note on the right. Hover a line to highlight it.

0

One element

It is the minimum and the maximum. No comparison.

1

Two elements

One comparison orders the pair: the smaller is the min, the larger is the max.

2

Combine two halves

One comparison for the minimums, one for the maximums.

Why stop at two elements?

If the recursion went all the way down to single elements, every combine would still cost 2 and the total would be 2n − 2, no better than the scan. The pair base case is what gives 3n/2 − 2.

    The recurrence

    T(n) = T(⌈n/2⌉) + T(⌊n/2⌋) + 2
    T(1) = 0,   T(2) = 1

    Two sub-problems of half the size plus two comparisons to combine them.

    Master theorem check

    • a = 2, b = 2, f(n) = Θ(1)
    • nlogba = n1 = n
    • f(n) = O(n1−ε) with ε = 1, so Case 1
    • T(n) = Θ(n)

    Check it in the lab

    For n = 8 the formula gives 3·8/2 − 2 = 10 comparisons.

    How the comparison count grows

    Hover the chart to read exact values. Click a legend item to hide a line.

    T(n) for n = 2 to 64

    Powers of two are exact

    For n = 2k the dots sit on the line 3n/2 − 2. At n = 64 that is 94 comparisons against 126 for the scan.

    Other sizes cost a little more

    The count stays between 3n/2 − 2 and 5n/3 − 2. The worst case is n = 3·2k: for n = 6 the algorithm uses 8 comparisons, not 7.

    It never depends on the data

    Sorted, reversed or random input all cost the same T(n). Best, average and worst case are identical.

    Comparisons saved versus the scan

    Powers of two save a little over 25%, easing toward 25% as n grows. Sizes 3·2k save the least, easing toward 16.7%.

    Is it optimal?

    Any algorithm that finds both the minimum and the maximum by comparing elements needs at least ⌈3n/2⌉ − 2 comparisons (Pohl, 1972; also in CLRS, section 9.1). Divide and conquer reaches that bound for every n = 2k, so there it cannot be beaten.

    What to remember

    The idea

    Cut the array in half again and again. Find the smallest and largest of each small piece, then join the pieces.

    Counting comparisons

    A piece with 1 number needs 0 comparisons. A piece with 2 numbers needs 1. Joining two pieces needs 2.

    The result

    For n = 2k we need only 3n/2 − 2 comparisons. The simple loop needs 2(n − 1). That is about 25% fewer.

    Cost and limit

    Time is Θ(n) and extra memory is O(log n). No method that compares numbers can do better than ⌈3n/2⌉ − 2.
